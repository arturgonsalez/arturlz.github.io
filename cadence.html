(02) — Context

Three products,
one customer,
zero cohesion
.

Cadence's parent company had stitched together a marketing suite by acquiring point tools — campaign builder, analytics, and CDP — each with its own design language, navigation, and data model.

Customers experienced it as one product. The team experienced it as three. Every feature meant duplicating UI work three times, with three different sets of inconsistencies to reconcile.

Acquired surfaces

(02)
Speed mandate

Leadership wanted feature parity across surfaces in two quarters. Without a system, the math didn't work — every ship was 3× the work.

(03)
Trust deficit

(03) — The Problem

Every feature shipped
three times — and three
subtly differently
.

A campaign-status badge looked like a pill in one product, a chip in another, and an inline label in the third. Engineering teams kept re-implementing the same primitives because the alternative — coordinating across squads — was harder than rebuilding.

The cost wasn't just velocity. Customers were quietly losing trust in a product that couldn't describe its own state consistently.

Failure mode 01
Token chaos

47 distinct shades of gray across the surfaces. 9 different "primary" buttons. Spacing inconsistent down to the 1px.

Failure mode 02
Pattern drift

Same task — say, scheduling a campaign — used 3 different interaction models. Users had to relearn within a single session.

Failure mode 03
No shared language

Designers and engineers used different names for the same thing. "Tag" meant 4 different concepts. Specs translated badly.

Deep Dive
Token Foundation

From 47 grays to 8.
From taste to system
.

Color tokens were where the system had to start — they were the most visibly broken and the cheapest place to demonstrate value. The original system had no semantic layer: every component referenced raw hex values, drifting independently over time.

The bet: introduce a semantic layer (text-primary, surface-raised, border-strong) on top of a primitive layer, and migrate components one at a time. The primitive scale stays small and intentional; semantics carry meaning across light, dark, and brand variants.

The research
AUDITED — 5 codebases, ~12k usages
CATEGORISED — 47 grays → 8 intents
DESIGNED — 3 themes from same scale
MIGRATED — Codemod-driven, automatable
01
Semantic layer over primitives

Every component references semantics ("text-primary"), never primitives. This decouples theme from implementation and made dark mode a 2-week feature instead of a quarter.

Trade-off → slower onboarding for new designers — semantics require thinking about intent. Worth it.
02
Codemod-first migration

Wrote a codemod that auto-replaced 80% of color usages. Manual review caught the ambiguous cases. 12k changes shipped in two weeks instead of two quarters.

Trade-off → invested 3 weeks in tooling before any visible UI shipped. Engineering buy-in was the unlock.
03
Themes as first-class

Light, dark, and a high-contrast accessibility theme all derived from the same token contract. No theme-specific overrides allowed.

Outcome → a new theme is a config file, not a project.

(09) — Reflection

What I'd do
differently.

What worked
Investing in tooling before pixels

The codemod migration was the single highest-leverage thing we built. Three weeks of infra investment unlocked twelve weeks of migration.

Making semantics, not styles, the contract

Components reference intent, not color. This decoupling made the dark mode launch trivial and pushed designers toward better systems thinking.

Embedding designers in squads

A central system team would have built the right thing for the wrong customer. Embedded designers carried system improvements upstream from real product work.

What I'd do differently
Earlier cross-functional governance

I underestimated how much governance needed PM and engineering co-ownership. Set that up earlier and the contribution model would have stabilised faster.

Ship the docs before the components

Several components shipped without good docs and got misused. Treat docs as gating, not a follow-up.

Quantify the baseline harder

The "60% faster" number is directional. Better baseline instrumentation would have let me defend the system's ROI more sharply.

"A design system is the slowest, most boring thing you can ship — until it's the only reason you can ship anything else."
